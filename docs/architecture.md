# Budget — архітектурна записка перед початком реалізації

> **Статус документа:** затверджена архітектурна основа, етап до реалізації.
> **Робоча назва продукту:** `Budget` (не остаточна, див. O-1).
> **Що зафіксовано:** стек, обов'язкові вимоги, шари, межі сховища та дизайн-системи, пакування, CI.
> **Що свідомо НЕ зафіксовано:** бізнес-модель і схема бази даних. Вони залежать від відкритих питань O-3, O-5, O-6; окремі частини моделі — також від O-10…O-14. O-9 блокує лише частину доменної моделі, що стосується боргу, і залежні від неї частини схеми бази. Правила бюджетного періоду (O-4) вирішено — A-18, ADR 0002. Механіку доходів і джерел витрат (O-2) вирішено — A-19, ADR 0003.
>
> Структури файлів і каталогів, описані нижче, є **цільовими**. Вони ще не створені в репозиторії.

## 1. Затверджено

**Стек:** Python 3.12, PySide6-Essentials, SQLite, uv, pytest, pytest-qt, ruff, PyInstaller у режимі onedir, Inno Setup 6, GitHub Actions на `windows-latest`.

| Код | Рішення | Що з нього випливає для реалізації |
|---|---|---|
| A-1 | Інсталятор `.exe` (Inno Setup) | Основний спосіб розповсюдження. |
| A-2 | **Q1:** встановлення лише для поточного користувача, без прав адміністратора | `PrivilegesRequired=lowest`, вибору режиму немає. Застосунок ставиться в `%LOCALAPPDATA%\Programs\<ProductName>`. Запис для видалення — в розділі реєстру поточного користувача (HKCU). |
| A-3 | Ярлики на Desktop і в Start Menu створюються автоматично | Записи `{autodesktop}` і `{autoprograms}` у секції `[Icons]`, без галочки, яку можна зняти. |
| A-4 | Штатне видалення | Видаляються файли застосунку, ярлики й запис у реєстрі. |
| A-5 | **Q2:** дані користувача при видаленні **не видаляються** | Дані не видаляються під час звичайної деінсталяції. Видалити їх можна лише явною дією користувача: окрема явно підписана галочка «Видалити також мої дані», **вимкнена за замовчуванням**. Її показує власне вікно в деінсталяторі. **Тихе видалення (`/SILENT`) ніколи не видаляє дані користувача, незалежно від стану цієї інтерактивної опції** (див. AC-1 у розділі 7). |
| A-6 | **Q3:** перший реліз без цифрового підпису | Підпис не блокує розробку. Для нього в конвеєрі передбачено окремий крок, який вмикається лише за наявності секрету (розділ 5.5). |
| A-7 | **Q4:** `Budget` — робоча назва | `product.toml` — єдине джерело ідентичності продукту. Назва продукту (`<ProductName>`), видавець (`<Publisher>`), `AppId`, ідентифікатор для панелі завдань (`<AppUserModelID>`), назва теки даних (`<DataDirectoryName>`), ім'я виконуваного файлу (`<ExecutableName>`) і базова назва інсталятора (`<InstallerBaseName>`) **ніде не прописуються вручну**. Вони читаються з `product.toml`. `AppId` поки тимчасовий; фінальний фіксується разом із назвою. |
| A-8 | **Q5:** кілька валют, перший реліз орієнтований на UAH | Валюта зберігається разом із кожною грошовою сумою там, де цього вимагає модель. Кількість знаків після коми береться з довідника валют (UAH — 2). Скласти суми в різних валютах неможливо — це помилка. Курсів і автоматичної конвертації немає. |
| A-9 | **Q6:** інтерфейс українською, з підтримкою локалізації | Усі тексти проходять через механізм перекладу Qt. Числа, дати й валюти форматуються з урахуванням мови (`QLocale`, `uk_UA`). Англійського перекладу поки немає, але його додавання не має вимагати переписування інтерфейсу. |
| A-10 | **Q7:** отриманий, але ще не розподілений дохід | Дохід може бути отриманий, але ще не розподілений між бюджетними напрямками чи категоріями. Така сума існує окремо від уже розподіленого бюджету. Термін і бізнес-модель визначаються окремо разом із власником продукту. **Назв у коді наперед не вводимо.** **Уточнено:** A-19, ADR 0003 — «розподіл» означає фактичну витрату. |
| A-11 | **Q8:** бюджетний період — окрема сутність з датою початку й датою завершення | Місяць лише як типовий варіант. Жодних прихованих «календарних місяців» у логіці. |
| A-12 | **Q9:** Windows 10 і 11, лише x64 | Збірки для ARM немає. |
| A-13 | **Q10:** portable ZIP необов'язковий і вторинний | Якщо він буде, дані зберігаються там само, де й у встановленій версії. Окремого «portable-режиму» зберігання немає. Основний спосіб розповсюдження — інсталятор. |
| A-14 | Дизайн-система з централізованими токенами | Кольори прописані лише в `ui/theme/`. |
| A-15 | SQLite з WAL, STRICT, атомарними транзакціями; гроші без `float`; резервні копії, відновлення, міграції | Розділ 5.3 і Додаток B. |
| A-16 | Окремі шари domain / storage / services / ui | Розділ 5.2. |
| A-17 | Власна іконка застосунку | Перелік потрібних файлів — у розділі 5.4. Стандартні іконки Python, PySide6, Qt чи Inno Setup не використовуються. |
| A-18 | **O-4:** бюджетний період, базовий мінімум, залишок і борг | Типовий бюджетний період — календарний місяць (з першого по останній день). Періоди не перетинаються, але можуть мати розриви. Доходи й витрати існують незалежно від періоду й не зобов'язані йому належати. Базовий мінімум — сума, яку користувач сам вводить для кожного періоду як орієнтир; це не план і не ліміт, і він не визначає борг. Борг — окреме реальне фінансове зобов'язання, що виникає лише при фактичному залученні позикових коштів. «Залишок» — окреме поняття, яке не є боргом. Деталі — ADR 0002. |
| A-19 | **O-2:** доходи, джерела витрат, нерозподілений залишок і накопичення | Кожен фактично отриманий дохід — окреме джерело коштів із власним залишком; до завершення бюджетного періоду доходи не об'єднуються в спільний пул. Джерело кожної витрати обирає лише користувач: активний дохід, «Загальний нерозподілений залишок» (навіть за наявності активних доходів) або накопичення («банка»); автоматичного вибору джерела (FIFO, LIFO тощо) немає. Витрата зменшує залишок саме обраного джерела. **Одна витрата — одне джерело**; фінансування однієї потреби з двох джерел — це дві окремі витрати. Якщо сума витрати перевищує залишок обраного джерела, збереження витрати блокується: від'ємного залишку, автоматичного добору, зміни джерела чи поділу витрати немає — рішення за користувачем. «Розподілено» означає «фактично витрачено»; стану «розподілено, але не витрачено» немає. Повністю витрачений дохід автоматично отримує статус «Завершений» і зберігається в історії (без видалення). Наприкінці періоду невикористані залишки доходів консолідуються в загальний нерозподілений залишок без нового доходу чи переказу. Загальний доступний залишок = загальний нерозподілений залишок + залишки накопичень + залишки активних доходів. Окремі залишки доходів не означають моделі банківських рахунків (O-3). Базовий мінімум і борг — окремо від O-2. Деталі — ADR 0003. |

### Терміни (A-18)

Поняття **базовий мінімум**, **фактичні витрати**, **перевищення базового мінімуму**, **залишок** і **борг** — різні й не ототожнюються. Визначення — в ADR 0002. Термін «перевитрата» не використовується як синонім перевищення базового мінімуму.

### Терміни (A-19)

**Конкретний дохід** — окреме джерело фактично отриманих коштів із власним залишком (не категорія, не резерв, не рахунок). **Джерело витрати** — активний дохід, «Загальний нерозподілений залишок» або накопичення; одна витрата має рівно одне джерело, яке обирає користувач. **Завершений дохід** — дохід із нульовим залишком; прибирається з активних джерел, але зберігається в історії. **Загальний нерозподілений залишок** — окреме джерело, до якого наприкінці бюджетного періоду консолідуються невикористані залишки доходів. **Розподіл** — фактична витрата, а не план. **Накопичення («банка»)** — накопичувальна категорія й допустиме джерело витрати; не рахунок і не заблоковані кошти. **Загальний доступний залишок** — загальний нерозподілений залишок разом із залишками накопичень і активних доходів. Визначення — в ADR 0003.

### Дизайн-рев'ю

**Візуальний напрям зафіксовано:**
- premium;
- беж і приглушений зелений (beige + muted green);
- редакційний характер (editorial);
- стриманість (restrained);
- багато вільного простору (whitespace).

**Заборонено:**
- «фінтех»-синій;
- кислотний зелений;
- glassmorphism;
- надмірні тіні;
- візуальний шум.

Hex-коди з Додатка C — **попередні дизайн-токени, а не фінальний дизайн**. Від них не переходимо безпосередньо до масової реалізації інтерфейсу. Окремий design review обов'язковий після визначення основних екранів (R-6).

## 4. Відкриті питання (OPEN QUESTIONS)

Тут лише те, що реально впливає на архітектуру або перший реліз. **Відкриті питання залишаються відкритими; відповіді на них у цьому документі не приймаються.** Вирішені питання позначено окремо нижче.

- **O-1. Фінальна назва, видавець та `AppId` (R-8).** Вирішувати зараз не потрібно. Але є жорстке обмеження: інсталятор розпізнає попередню версію **лише за `AppId`**. Якщо публічний реліз вийде з тимчасовим `AppId`, а потім `AppId` зміниться, у користувачів буде дві окремі установки, а теку з даними доведеться переносити. Тому до першого публічного релізу потрібні фінальні назва, видавець і `AppId`. Внутрішні тестові збірки можна випускати з тимчасовими значеннями.
- **O-3. Рахунки в першому релізі (R-2).**
- **O-5. Семантика «базова / бажана» витрата (R-4).**
- **O-6. Фінансові цілі в першому релізі (R-5).**
- **O-7. Екрани першого релізу (R-6).** Передумова дизайн-рев'ю.
- **O-8. Обмеження щодо хвилин GitHub Actions (технічне).** Якщо репозиторій приватний, хвилини Windows-runner'ів витрачаються з підвищеним коефіцієнтом, а безкоштовний ліміт обмежений. Тому важкі Windows-завдання запускаються лише там, де вони потрібні (розділ 5.6). Чи є обмеження на хвилини CI?
- **O-9. Модель боргу.** Визначити модель реального фінансового боргу: створення, погашення, часткове погашення, види боргу, можливі зв'язки з витратами та інші правила. Блокує лише проєктування й реалізацію частини доменної моделі, що стосується боргу, і залежних від неї частин схеми бази.
- **O-10. Доходи на межі бюджетних періодів.** Що відбувається із залишком доходу, отриманого в дні, які не входять у жоден бюджетний період.
- **O-11. Редагування та видалення доходів.** Як редагування доходу чи його видалення користувачем впливає на залишки й витрати.
- **O-12. Кілька валют у джерелах і залишках.** Як окремі джерела, загальний нерозподілений залишок і загальний доступний залишок поводяться за кількох валют (з урахуванням A-8).
- **O-13. Накопичення в аналізі періоду.** Як витрати на накопичення й з накопичень враховуються в аналізі фактичних витрат періоду, зокрема щодо базового мінімуму.
- **O-14. Поняття «планування».** Що саме охоплює «планування» з ADR 0002, крім введення базового мінімуму.

**Вирішені питання:**
- ~~O-2. Модель нерозподіленого доходу (R-1).~~ **Вирішено** → A-19, ADR 0003. Питання поза механікою джерел винесено в O-10…O-14.
- ~~O-4. Правила бюджетних періодів і перенесення залишків/перевитрат (R-3).~~ **Вирішено** → A-18, ADR 0002.

O-3, O-5, O-6 не блокують підготовку каркаса проєкту: тулінг, CI, тему, механізми сховища. Але вони **блокують проєктування domain-моделі та схеми бази**. До відповідей на них жодні доменні сутності (рахунки, доходи, витрати, цілі тощо) та таблиці не проєктуються. Бізнес-правила бюджетного періоду (ADR 0002) і механіку доходів та джерел витрат (ADR 0003) визначено, але їхня структура в базі ще не проєктується. O-10…O-14 стосуються окремих частин моделі й мають бути вирішені до проєктування цих частин.

**O-9 (модель боргу)** блокує лише проєктування та реалізацію частини доменної моделі, що стосується боргу, і залежних від неї частин схеми бази. O-9 **не блокує** проєктування інших уже визначених частин продукту, зокрема бюджетного періоду, базового мінімуму, доходів, витрат, залишку та інших доменних правил, які будуть визначені окремо.

### 5.1. Цільова структура репозиторію

### 5.2. Шари та напрям залежностей

```
ui ──▶ services ──▶ domain
          │            ▲
          └──▶ storage ┘
platform ◀── app (складає все разом)
```

| Шар | Що містить | Що йому заборонено |
|---|---|---|
| `domain` | Сутності, `Money`, правила розрахунку (наприклад, залишок, перевищення базового мінімуму), перевірки | Імпортувати Qt, `sqlite3`, файлову систему; використовувати `float` |
| `storage` | З'єднання з базою, репозиторії, міграції, резервні копії, перевірка цілісності | Містити бізнес-правила; імпортувати Qt |
| `services` | Сценарії (один сценарій — одна транзакція), координація domain і storage | Імпортувати Qt; писати SQL напряму |
| `ui` | Віджети, екрани, тема, форматування для показу | Писати SQL; містити бізнес-правила; задавати кольори поза `theme/` |
| `platform` | Шляхи Windows, блокування від запуску другої копії, AppUserModelID | Містити бізнес-логіку |

- Межі між шарами перевіряє тест на імпорти в CI. Інструмент на зразок import-linter можна додати лише за окремим рішенням, бо це нова залежність.
- Логіка не залежить від Qt. Тому `domain`, `storage` і `services` тестуються без інтерфейсу, зокрема на Linux.

### 5.3. Межі даних і сховища

- **Розташування.** Користувацькі дані зберігаються в `%LOCALAPPDATA%\<DataDirectoryName>\` (значення з `product.toml`):
  - `budget.db` (+ `-wal`, `-shm`);
  - `backups/`;
  - `settings.json`;
  - `logs/`.

  Шлях один і той самий для встановленої та portable-версії. Тека програми й «Документи» для даних не використовуються: «Документи» часто синхронізує OneDrive, а це конфліктує з файлами WAL.
- **Підключення.** При кожному підключенні виставляються `journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON`, і всі таблиці мають тип `STRICT`.
- **Транзакції.** Відкриває їх лише шар `services` (`BEGIN IMMEDIATE`): одна дія користувача — одна транзакція. `storage` не робить commit самостійно.
- **Гроші.** У домені грошове значення представлене типом `Money` разом із кодом валюти. Для зберігання суми використовується `INTEGER` у мінімальних одиницях валюти. Конкретне розташування коду валюти в схемі SQLite визначається після рішення O-3; схема бази цим пунктом не проєктується. Користувацьке введення розбирається з рядка в `Decimal`, правило округлення задається явно. `float` для грошей не використовується; це перевіряється в CI.
- **Запуск:**
  1. блокування від запуску другої копії;
  2. `quick_check`;
  3. щоденна резервна копія;
  4. міграції — лише після обов'язкової резервної копії, кожна в окремій транзакції;
  5. нумерація міграцій лише вперед, номер схеми в `user_version`.
- **Пошкодження бази.** Застосунок нічого не записує, перейменовує пошкоджений файл і пропонує відновитися з останньої справної копії.
- **Налаштування.** Записуються атомарно: тимчасовий файл, потім `os.replace`. **У базі даних налаштування інтерфейсу не зберігаються.**
- **Видалення.** Деінсталятор видаляє цю теку **лише** тоді, коли користувач явно поставив галочку (A-5). Тихе видалення (`/SILENT`) її не видаляє ніколи (AC-1).

Детальні вимоги — Додаток B.

### 5.4. Межі дизайн-системи

- **`ui/theme/tokens.py`** — єдине місце зі значеннями. Значення мають два рівні:
  - **базова палітра**, наприклад `sage-300`;
  - **семантичні ролі**: `bg`, `surface`, `text`, `text-muted`, `primary`, `danger`…

  Компоненти звертаються **лише до семантичних ролей**. Тому палітру можна змінити, а пізніше й додати темну тему, не чіпаючи компоненти.
- **Категорії токенів:** кольори, типографіка (гарнітури, розміри, товщини, цифри однакової ширини для сум), відступи, радіуси, тіні (не більше одного стриманого рівня), розміри елементів, стани (hover / pressed / focus / disabled / error), іконки.
- **Як токени потрапляють у віджети.** Шаблон QSS отримує значення з токенів, плюс налаштовується `QPalette`. Іконки інтерфейсу — монохромні SVG, які перефарбовуються кольором з токенів. Кандидат — набір Lucide (ліцензія ISC).
- **Контроль у CI:**
  - тест шукає hex-кольори поза `ui/theme/`;
  - тест перевіряє контраст пар «текст/фон» за WCAG AA.
- **Статус значень.** Усі нинішні значення (Додаток C) позначені як попередні до завершення дизайн-рев'ю (R-7).
- **Тексти інтерфейсу.** Перекладні рядки — лише через механізм Qt (`tr`). Форматування сум і дат — лише через `QLocale` (українська мова: кома як десятковий роздільник, три форми множини).
- **Іконка застосунку.** Потрібні такі файли:
  - `assets/icon/budget.svg` — векторний оригінал, єдине джерело;
  - `assets/icon/budget.ico` з розмірами 16, 20, 24, 32, 40, 48, 64, 256 (256 у стисненні PNG);
  - `assets/icon/png/` — PNG тих самих розмірів для вікна (`QIcon`);
  - `assets/installer/` — графіка майстра встановлення: велика бічна (164×314 та масштаби 125–250 %) і мала (55×55 та масштаби).

  Один і той самий набір використовують `.exe`, інсталятор, ярлики, запис видалення й вікно. Рекомендація для design review: окремо перевірити читабельність іконки на малих розмірах 16–24 px; за потреби може бути створено спрощений варіант малюнка.
- **Обмеження Qt, які треба врахувати в дизайні:**
  - QSS не підтримує `box-shadow` і анімацію переходів. Тіні — через `QGraphicsDropShadowEffect` (точково, бо дорогий у відмальовуванні) або відтінками й тонкими рамками.
  - Рекомендація: за замовчуванням зберігати системну рамку вікна, бо власна безрамкова шапка може порушити прилипання вікон, масштабування та доступність. На Windows 11 колір заголовка можна підлаштувати під палітру через системний API. Остаточне рішення щодо рамки вікна та оформлення вікна (chrome) приймається під час design review.

### 5.5. Структура пакування та релізу

```
pyproject.toml (версія) ─┐
product.toml (назва…) ───┼─▶ PyInstaller (onedir, іконка, ресурс версії)
                         │        └─▶ dist/<ExecutableName>/<ExecutableName>.exe
                         │              ├─▶ [крок «підпис»: .exe]   ← вимкнено (Q3)
                         │              ├─▶ ISCC /DAppVersion /DAppId /DAppName …
                         │              │     └─▶ <InstallerBaseName>-x.y.z.exe
                         │              │           └─▶ [крок «підпис»: інсталятор] ← вимкнено
                         │              └─▶ (необов'язково) <ExecutableName>-x.y.z-portable.zip
                         └─▶ SHA256SUMS.txt → GitHub Release
```

- **Inno Setup** отримує всі ідентифікатори як параметри компіляції. У `.iss` вони не прописані.
- **Як потім увімкнути підпис (Q3):**
  - у самому конвеєрі вже є окремі кроки підпису, які вмикаються за наявності секрету сертифіката;
  - у Inno Setup для цього є директиви `SignTool` і `SignedUninstaller`.

  Підпис додається без перебудови пакування.
- **Перевірки після збірки:**
  - `<ExecutableName>.exe --self-check` запускається без екрана й завершується з кодом 0;
  - тихе встановлення;
  - перевірка, що є файли, обидва ярлики й запис у HKCU;
  - тихе видалення;
  - перевірка, що **дані залишилися** (AC-1).

Деталі налаштувань Inno Setup і механізм ярликів — Додаток A.

### 5.6. Структура CI

| Workflow | Коли запускається | Runner | Що робить |
|---|---|---|---|
| `ci.yml` / `lint` | кожен push і PR | `ubuntu-latest` | `ruff check`, `ruff format --check` |
| `ci.yml` / `core-tests` | кожен push і PR | `ubuntu-latest` | pytest для `domain`, `storage`, `services`; тести меж шарів і заборони `float` |
| `ci.yml` / `windows-tests` | PR у `main` і push у `main` | `windows-latest` | Повний pytest, включно з тестами інтерфейсу (pytest-qt, `QT_QPA_PLATFORM=offscreen`) і тестами токенів |
| `ci.yml` / `build-check` | push у `main` (або вручну) | `windows-latest` | PyInstaller і `--self-check`, без інсталятора |
| `release.yml` | тег `v*` або ручний запуск | `windows-latest` | Тести, PyInstaller, (підпис), Inno Setup, перевірка встановлення й видалення, (ZIP), SHA256, GitHub Release |

- Inno Setup встановлюється в робочому процесі явно (наприклад `choco install innosetup`), без розрахунку на образ runner'а.
- Python і uv фіксуються однаковими версіями в усіх завданнях.
- Windows 10 у GitHub Actions недоступна (runner'и — Windows Server). Тому **ручна перевірка першого інсталятора на Windows 10 і 11** входить до списку перевірок перед релізом.
- Тимчасовий `AppId` дозволений для внутрішніх тестових збірок і заборонений для першого та будь-якого публічного релізу. `release.yml` має блокувати саме **публічний** реліз із тимчасовим `AppId` (див. O-1). Це не означає, що конвеєр для внутрішніх тестових збірок потрібно реалізовувати вже зараз.

## 6. Ризики, що лишаються

| Ризик | Рівень | Що робимо |
|---|---|---|
| Тимчасовий `AppId` потрапить у публічний реліз | **Високий за наслідками** | O-1: фінальні ідентифікатори обов'язкові перед першим публічним релізом; `release.yml` блокує **публічний** реліз із тимчасовим `AppId`. Внутрішні тестові збірки з тимчасовим `AppId` дозволені. |

| Хвилини Windows-runner'ів (O-8) | Низький або середній | Важкі Windows-завдання не запускаються на кожен push. |
| Інструменти перекладу Qt (`pyside6-lupdate`, `pyside6-lrelease`) у пакеті Essentials | Низький | Перевірити наявність під час підготовки середовища; запасний варіант — стандартний модуль `gettext`. |
| Розмір збірки PySide6 | Низький | Лише пакет Essentials, виключення невикористаних модулів Qt. Розмір виміряти після першої збірки. |
| Обмеження QSS (немає тіней і анімацій) | Низький | Дизайн-система будується з урахуванням цього (5.4). |
| Наявність Inno Setup на runner'і | Низький | Явне встановлення в робочому процесі CI. |
| Синхронізація OneDrive і файли WAL | Низький | База в `%LOCALAPPDATA%` (5.3). |
| Дотримання ліцензії LGPL для Qt | Низький | Динамічне підключення (його дає PyInstaller) + файл з ліцензіями в дистрибутиві (`packaging/licenses/`). |

| AC-6 | `<ExecutableName>.exe --self-check` завершується з кодом 0. | `ci.yml` / `build-check` і `release.yml`. |

## Додаток A. Деталі інсталятора

> Цей додаток є технічною деталізацією вже затверджених рішень розділів 1–5. Він не вводить нових продуктових або архітектурних рішень. Якщо положення цього додатка суперечить затвердженому рішенню або відкритому питанню, пріоритет має затверджене рішення та/або відкрите питання.
>
> Плейсхолдери `<ProductName>`, `<Publisher>`, `<AppUserModelID>`, `<DataDirectoryName>`, `<ExecutableName>`, `<InstallerBaseName>` означають значення з `product.toml` (A-7).

### A.1. Конвеєр збірки

```
джерельний код → PyInstaller (onedir) → dist\<ExecutableName>\<ExecutableName>.exe + бібліотеки
                                          ├─→ Inno Setup (ISCC) → <InstallerBaseName>-x.y.z.exe
                                          └─→ ZIP (необов'язково) → <ExecutableName>-x.y.z-portable.zip
```

### A.2. Ключові налаштування Inno Setup (`packaging/inno/budget.iss`)

| Параметр | Значення | Навіщо |
|---|---|---|
| `AppId` | GUID із `product.toml`. Поки **тимчасовий**; фінальний фіксується разом із назвою (O-1) і після першого публічного релізу **ніколи не змінюється** | Інсталятор розпізнає попередню версію й оновлює її, а не ставить другу копію. |
| `AppName` / `AppVersion` / `AppPublisher` | з `product.toml` і `pyproject.toml`, передаються через `ISCC /D…`; так само передаються `<ExecutableName>` і `<InstallerBaseName>` | Одне джерело для всього. |
| `PrivilegesRequired` | `lowest`, без вибору режиму (A-2) | Встановлення лише для поточного користувача, без прав адміністратора. |
| `DefaultDirName` | `{autopf}\<ProductName>` | За режиму `lowest` це `%LOCALAPPDATA%\Programs\<ProductName>`. |
| `SetupIconFile` | `assets\icon\budget.ico` | Іконка самого інсталятора. |
| `UninstallDisplayIcon` | `{app}\<ExecutableName>.exe` | Іконка в списку встановлених програм. |
| `WizardImageFile` / `WizardSmallImageFile` | власна графіка з `assets/installer/` | Прибирає стандартне оформлення Inno. |
| `CloseApplications=yes` + `AppMutex` | — | Перед оновленням інсталятор просить закрити запущений застосунок. |
| `ArchitecturesAllowed` / `ArchitecturesInstallIn64BitMode` | `x64compatible` | Лише 64-бітна збірка (A-12). |
| `SignTool` / `SignedUninstaller` | не задані до появи сертифіката | Підпис вмикається пізніше без перебудови (A-6). |

### A.3. Як саме з'явиться ярлик на Desktop

У секції `[Icons]` будуть два записи:

```
Name: "{autoprograms}\<ProductName>"; Filename: "{app}\<ExecutableName>.exe"; AppUserModelID: "<AppUserModelID>"
Name: "{autodesktop}\<ProductName>";  Filename: "{app}\<ExecutableName>.exe"; AppUserModelID: "<AppUserModelID>"
```

- **Ярлик обов'язковий.** Стандартний шаблон Inno робить ярлик на робочому столі необов'язковою галочкою, вимкненою за замовчуванням. Тут ярлик навмисно **не прив'язаний** до параметра `Tasks`, тому створюється завжди.
- За встановлення для поточного користувача `{autodesktop}` — це робочий стіл поточного користувача.
- Іконку ярлик бере з ресурсу `<ExecutableName>.exe`, куди її вбудовує PyInstaller.
- Однаковий `AppUserModelID` у ярлику та в застосунку потрібен, щоб на панелі завдань показувалася іконка застосунку, а не іконка Python. Значення береться з `product.toml`.
- Під час видалення обидва ярлики прибираються автоматично.
- Назва ярлика — `<ProductName>` (зараз робоча назва `Budget`); вона зміниться разом із назвою продукту (O-1).

### A.4. Видалення і дані користувача

- Inno автоматично реєструє запис для штатного видалення Windows у HKCU.
- Видаляються файли застосунку, ярлики й запис у реєстрі.
- Тека даних `%LOCALAPPDATA%\<DataDirectoryName>\` за замовчуванням **залишається**.
- Інтерактивне видалення показує власне вікно з галочкою «Видалити також мої дані», **вимкненою за замовчуванням**.
- **`/SILENT` ніколи не видаляє дані користувача, незалежно від стану інтерактивної опції** (AC-1).

## Додаток B. Вимоги до безпеки даних (DS-1…DS-10)

> Цей додаток є технічною деталізацією вже затверджених рішень розділів 1–5. Він не вводить нових продуктових або архітектурних рішень. Якщо положення цього додатка суперечить затвердженому рішенню або відкритому питанню, пріоритет має затверджене рішення та/або відкрите питання.

| № | Вимога | Як реалізується |
|---|---|---|
| DS-1 | Гроші | Кожне грошове значення має валюту. Сума зберігається як `INTEGER` у мінімальних одиницях валюти; фізичне розташування коду валюти в схемі бази визначається після рішення O-3. У логіці — тип `Money`, усередині якого `int` або `Decimal`. Введення користувача розбирається з рядка в `Decimal`; правило округлення фіксується явно. **`float` заборонений** — це перевіряють тест і пошук у CI. |
| DS-2 | Атомарність | Одна дія користувача — одна транзакція (`BEGIN IMMEDIATE … COMMIT`, відкат при помилці). Транзакції керуються явно, без неявної поведінки модуля `sqlite3`. |
| DS-3 | Стійкість до переривань | `journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON`. Незавершена транзакція (збій живлення, примусове закриття) автоматично відкочується. |
| DS-4 | Цілісність | Таблиці `STRICT`, обмеження `CHECK`, зовнішні ключі. `PRAGMA quick_check` при запуску, повний `integrity_check` перед резервною копією. |
| DS-5 | Резервні копії | Через вбудоване API `Connection.backup()` (узгоджена копія під час роботи). Коли: щодня при першому запуску, **обов'язково перед кожною міграцією**, перед відновленням, на вимогу. Ротація за замовчуванням: 7 щоденних + 4 щотижневі + 12 щомісячних. Кожна копія після запису перевіряється на цілісність. |
| DS-6 | Відновлення | Якщо перевірка виявила пошкодження: застосунок **нічого не записує**, пошкоджений файл перейменовує й зберігає, пропонує відновлення з останньої справної копії. |
| DS-7 | Міграції | Нумеровані, лише вперед. Версія схеми — у `PRAGMA user_version`. Кожна міграція — одна транзакція після резервної копії. Тести проганяють увесь ланцюжок міграцій від порожньої бази. |
| DS-8 | Один процес | Блокування через `QLockFile`: друга копія застосунку не відкриє ту саму базу на запис. |
| DS-9 | Розташування даних | База — у `%LOCALAPPDATA%\<DataDirectoryName>\`, а не в теці програми й не в «Документах». Налаштування — JSON з атомарним записом (тимчасовий файл + `os.replace`). |
| DS-10 | Експорт | Пізніше (D-6) — експорт у відкритий формат (CSV/JSON) як незалежний від бази шлях порятунку даних. |

Схема бази, перелік таблиць і доменні сутності **тут не визначаються** — вони залежать від O-3, O-5, O-6 (окремі частини — також від O-10…O-14); частина, що стосується боргу, — також від O-9.

## Додаток D. Обґрунтування стеку

> Цей додаток є технічною деталізацією вже затверджених рішень розділів 1–5. Він не вводить нових продуктових або архітектурних рішень. Якщо положення цього додатка суперечить затвердженому рішенню або відкритому питанню, пріоритет має затверджене рішення та/або відкрите питання.

| Шар | Інструмент | Чому він |
|---|---|---|
| Мова | Python 3.12 | Зріла підтримка в PySide6 і PyInstaller; у `Decimal` вбудовано точну грошову арифметику. |
| Інтерфейс | PySide6 (Qt 6), лише пакет `PySide6-Essentials` | Стилізація через QSS дозволяє повністю власний вигляд. Ліцензія LGPL. Пакет Essentials зменшує розмір збірки. |

| Інсталятор | Inno Setup 6 | Повністю покриває вимоги A-1…A-5; безкоштовна збірка в CI одним кроком. |
| CI та випуски | GitHub Actions, `windows-latest` | Збірка й перевірка Windows-артефактів без локальної Windows-машини. |

**Розглянуті альтернативи:**
- **.NET (WPF/WinUI).** Дизайн буде повністю власний, тому нативні елементи Windows перевагою не стають. Розробка йшла б лише через CI або на Windows-машині.
- **Electron або Tauri.** Два стеки замість одного й важчий застосунок без виграшу для локального бюджетного інструмента.
- **Інсталятори WiX/MSI.** Складніші й без переваги для встановлення одним користувачем. **NSIS** можливий, але його скрипти важче супроводжувати, ніж Inno.

**Розподіл тестів між середовищами.**
- Доменна логіка й сховище — чистий Python без Qt; тестуються на Linux.
- Тести інтерфейсу й збірка — на Windows CI.
