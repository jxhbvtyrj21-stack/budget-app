# Budget — архітектурна записка перед початком реалізації

> **Статус документа:** затверджена архітектурна основа, етап до реалізації.
> **Назва продукту:** `Budget` (остаточна, A-31, ADR 0015).
> **Що зафіксовано:** стек, обов'язкові вимоги, шари, межі сховища та дизайн-системи, пакування, CI.
> **Що свідомо НЕ зафіксовано:** схема бази даних і конкретні доменні сутності. Відкритих O-питань немає: бізнес-модель першого релізу визначено рішеннями A-18…A-36 і ADR 0002–0020. Правила бюджетного періоду (O-4) вирішено — A-18, ADR 0002. Механіку доходів і джерел витрат (O-2) вирішено — A-19, ADR 0003. Рахунки (O-3) вирішено — A-20, ADR 0004. Поділ витрат на «базові / бажані» (O-5) вирішено — A-21, ADR 0005. Фінансові цілі (O-6) вирішено — A-22, ADR 0006. Властивості та життєвий цикл накопичень (O-15) вирішено — A-23, ADR 0007. Валюту першого релізу (O-12) вирішено — A-24, ADR 0008. Життєвий цикл доходу й модель календарного місяця (O-11) вирішено — A-25, ADR 0009. Календарну належність фінансових операцій і стартові залишки (Q151–Q167) зафіксовано — A-26, ADR 0010. Редагування операцій і межі первинного налаштування (Q168–Q173) зафіксовано, O-10 закрито як неактуальне — A-27, ADR 0011. Редагування поповнень, незавершене первинне налаштування й архівування накопичень (Q174–Q185) зафіксовано — A-28, ADR 0012. Межі архівування накопичень і межу первинного налаштування (Q186–Q190) зафіксовано — A-29, ADR 0013. Редагування метаданих операцій архівованого накопичення (Q191) зафіксовано — A-30, ADR 0014. Ідентичність продукту (O-1), екрани (O-7), хвилини CI (O-8), модель боргу (O-9), планування (O-14) й аналіз періоду (O-13) вирішено — A-31…A-36, ADR 0015–0020. Дизайн-рев'ю (R-7) завершено — A-37, ADR 0021, `docs/design/`. Чотири питання дизайн-рев'ю вирішено — A-38, ADR 0022.
>
> Структури файлів і каталогів, описані нижче, є **цільовими**. Вони ще не створені в репозиторії.

## 1. Затверджено

**Стек:** Python 3.12, PySide6-Essentials, SQLite, uv, pytest, pytest-qt, ruff, PyInstaller у режимі onedir, Inno Setup 6, GitHub Actions на `windows-latest`.

| Код | Рішення | Що з нього випливає для реалізації |
|---|---|---|
| A-1 | Інсталятор `.exe` (Inno Setup) | Основний спосіб розповсюдження. |
| A-2 | **Q1:** встановлення лише для поточного користувача, без прав адміністратора | `PrivilegesRequired=lowest`, вибору режиму немає. Застосунок ставиться в `%LOCALAPPDATA%\Programs\<ProductName>`. Запис для видалення — в розділі реєстру поточного користувача (HKCU). |
| A-3 | Ярлики на Desktop і в Start Menu створюються автоматично | Записи `{autodesktop}` і `{autoprograms}` у секції `[Icons]`, без галочки, яку можна зняти. |
| A-4 | Штатне видалення | Видаляються файли застосунку, ярлики й запис у реєстрі. |
| A-5 | **Q2:** дані користувача при видаленні **не видаляються** | Дані не видаляються під час звичайної деінсталяції. Видалити їх можна лише явною дією користувача: окрема явно підписана галочка «Видалити також мої дані», **вимкнена за замовчуванням**. Її показує власне вікно в деінсталяторі. **Тихе видалення (`/SILENT`) ніколи не видаляє дані користувача, незалежно від стану цієї інтерактивної опції** (див. AC-1 у розділі 7). |
| A-6 | **Q3:** перший реліз без цифрового підпису | Підпис не блокує розробку. Для нього в конвеєрі передбачено окремий крок, який вмикається лише за наявності секрету (розділ 5.5). |
| A-7 | **Q4:** `Budget` — робоча назва | `product.toml` — єдине джерело ідентичності продукту. Назва продукту (`<ProductName>`), видавець (`<Publisher>`), `AppId`, ідентифікатор для панелі завдань (`<AppUserModelID>`), назва теки даних (`<DataDirectoryName>`), ім'я виконуваного файлу (`<ExecutableName>`) і базова назва інсталятора (`<InstallerBaseName>`) **ніде не прописуються вручну**. Вони читаються з `product.toml`. `AppId` поки тимчасовий; фінальний фіксується разом із назвою. **Уточнено:** A-31, ADR 0015 — `Budget` є остаточною назвою; остаточні значення ідентичності, зокрема `AppId`, визначено. |
| A-8 | **Q5:** кілька валют, перший реліз орієнтований на UAH | Валюта зберігається разом із кожною грошовою сумою там, де цього вимагає модель. Кількість знаків після коми береться з довідника валют (UAH — 2). Скласти суми в різних валютах неможливо — це помилка. Курсів і автоматичної конвертації немає. **Уточнено для першого релізу:** A-24, ADR 0008 — усі грошові величини лише в UAH; положення про кілька валют, довідник валют і зберігання валюти разом із сумою в першому релізі не застосовуються. |
| A-9 | **Q6:** інтерфейс українською, з підтримкою локалізації | Усі тексти проходять через механізм перекладу Qt. Числа, дати й валюти форматуються з урахуванням мови (`QLocale`, `uk_UA`). Англійського перекладу поки немає, але його додавання не має вимагати переписування інтерфейсу. |
| A-10 | **Q7:** отриманий, але ще не розподілений дохід | Дохід може бути отриманий, але ще не розподілений між бюджетними напрямками чи категоріями. Така сума існує окремо від уже розподіленого бюджету. Термін і бізнес-модель визначаються окремо разом із власником продукту. **Назв у коді наперед не вводимо.** **Уточнено:** A-19, ADR 0003 — «розподіл» означає фактичну витрату. |
| A-11 | **Q8:** бюджетний період — окрема сутність з датою початку й датою завершення | Місяць лише як типовий варіант. Жодних прихованих «календарних місяців» у логіці. **Замінено:** A-25, ADR 0009 — бюджетний період є календарним місяцем (часова зона `Europe/Kyiv`) без окремої сутності й окремого запису в базі даних. |
| A-12 | **Q9:** Windows 10 і 11, лише x64 | Збірки для ARM немає. |
| A-13 | **Q10:** portable ZIP необов'язковий і вторинний | Якщо він буде, дані зберігаються там само, де й у встановленій версії. Окремого «portable-режиму» зберігання немає. Основний спосіб розповсюдження — інсталятор. |
| A-14 | Дизайн-система з централізованими токенами | Кольори прописані лише в `ui/theme/`. |
| A-15 | SQLite з WAL, STRICT, атомарними транзакціями; гроші без `float`; резервні копії, відновлення, міграції | Розділ 5.3 і Додаток B. |
| A-16 | Окремі шари domain / storage / services / ui | Розділ 5.2. |
| A-17 | Власна іконка застосунку | Перелік потрібних файлів — у розділі 5.4. Стандартні іконки Python, PySide6, Qt чи Inno Setup не використовуються. |
| A-18 | **O-4:** бюджетний період, базовий мінімум, залишок і борг | Типовий бюджетний період — календарний місяць (з першого по останній день). Періоди не перетинаються, але можуть мати розриви. Доходи й витрати існують незалежно від періоду й не зобов'язані йому належати. **Уточнено для доходів:** A-25, ADR 0009 — бюджетний період є календарним місяцем без розривів; кожен дохід належить календарному місяцю свого створення; історичні доходи не додаються й не редагуються. Базовий мінімум — сума, яку користувач сам вводить для кожного періоду як орієнтир; це не план і не ліміт, і він не визначає борг. Борг — окреме реальне фінансове зобов'язання, що виникає лише при фактичному залученні позикових коштів. «Залишок» — окреме поняття, яке не є боргом. Деталі — ADR 0002. **Уточнено для витрат:** A-26, ADR 0010 — витрата належить календарному місяцю свого створення; після переходу місяця вона доступна лише для перегляду (підтверджено A-27, ADR 0011). |
| A-19 | **O-2:** доходи, джерела витрат, нерозподілений залишок і накопичення | Кожен фактично отриманий дохід — окреме джерело коштів із власним залишком; до завершення бюджетного періоду доходи не об'єднуються в спільний пул. Джерело кожної витрати обирає лише користувач: активний дохід, «Загальний нерозподілений залишок» (навіть за наявності активних доходів) або накопичення («банка»); автоматичного вибору джерела (FIFO, LIFO тощо) немає. Витрата зменшує залишок саме обраного джерела. **Одна витрата — одне джерело**; фінансування однієї потреби з двох джерел — це дві окремі витрати. Якщо сума витрати перевищує залишок обраного джерела, збереження витрати блокується: від'ємного залишку, автоматичного добору, зміни джерела чи поділу витрати немає — рішення за користувачем. «Розподілено» означає «фактично витрачено»; стану «розподілено, але не витрачено» немає. Повністю витрачений дохід автоматично отримує статус «Завершений» і зберігається в історії (без видалення). Наприкінці періоду невикористані залишки доходів консолідуються в загальний нерозподілений залишок без нового доходу чи переказу. **Уточнено:** A-25, ADR 0009 — дохід із нульовим залишком автоматично архівується; після тривалої перерви для минулих місяців діє спеціальна процедура «Перенести / Вилучити». Загальний доступний залишок = загальний нерозподілений залишок + залишки накопичень + залишки активних доходів. Окремі залишки доходів не означають моделі банківських рахунків (O-3). Базовий мінімум і борг — окремо від O-2. Деталі — ADR 0003. **Уточнено:** A-26, ADR 0010 — єдиний початковий баланс доходу з первинного налаштування зараховується до загального нерозподіленого залишку без створення доходу чи нового типу джерела. |
| A-20 | **O-3:** рахунки в першому релізі | Банківські рахунки не моделюються в першому релізі: немає рахунків, карток чи гаманців як доменних сутностей, балансів рахунків, фізичного місця зберігання грошей, прив'язки доходів і витрат до рахунків, переказів між рахунками й синхронізації з банківськими залишками. Окремі джерела доходів, загальний нерозподілений залишок і накопичення — логічні елементи бюджетної моделі, а не рахунки. O-2 не змінюється. Кредитні картки — O-9; місце коду валюти в SQLite — O-12 і модель `Money`. Деталі — ADR 0004. |
| A-21 | **O-5:** поділ витрат на «базові / бажані» | Поділ витрат на «базові / бажані» не входить до першого релізу й не є частиною доменної моделі: немає ознаки, окремої сутності, значення «не задано», вибору користувачем, поля в історичних витратах, участі в розрахунках, фільтрації, групуванні чи аналітиці. Інші властивості, структура та категоризація витрат цим рішенням не визначаються. Семантика базового мінімуму (ADR 0002) не змінюється; зв'язку між базовим мінімумом і цим поділом немає. Деталі — ADR 0005. |
| A-22 | **O-6:** фінансові цілі в першому релізі | Фінансові цілі входять до першого релізу, але не є окремою сутністю: функцію фінансової цілі виконує накопичення, створене користувачем для конкретного майбутнього фінансового результату (наприклад, «Заміна паркану», «Нова сантехніка», «Поїздка»). Одна широка сфера (наприклад, «ремонт») не означає одне накопичення. Окремої сутності «Фінансова ціль», окремого залишку цілі чи окремого джерела витрати «ціль» немає; формула загального доступного залишку не змінюється. Цільова сума, строк, статус і прогрес цим рішенням не вводяться й залишаються невизначеними (O-15). Правила накопичень з ADR 0003 не змінюються. Деталі — ADR 0006. |
| A-23 | **O-15:** властивості та життєвий цикл накопичень | Поповнення накопичення — спеціальний вид витрати з призначенням на конкретне накопичення; окремої операції «внесок» чи сутності «переказ» немає. **Звичайна витрата — одне джерело** (ADR 0003 не змінюється); **одне поповнення накопичення може використовувати кілька джерел, які користувач визначає вручну** (пізніше уточнення ADR 0007 саме для поповнення). Джерела поповнення — конкретні доходи й загальний нерозподілений залишок; інше накопичення джерелом поповнення бути не може, але залишається джерелом звичайної витрати. З кожного джерела — не більше його доступного залишку. Початковий залишок накопичення під час первинного запуску — окремий механізм налаштування, не дохід. Цільова сума — необов'язкова, не ліміт; строку немає. Статуси «Активне», «Досягнуте», «Закрите» змінюються лише вручну; закриття — лише при балансі 0; закрите накопичення можна поповнювати, витрачати з нього й повертати в «Активне», а також архівувати; фізичного видалення немає. Прогрес — похідний показник за наявності цільової суми. Деталі й невизначеності — ADR 0007. **Уточнено:** A-26, ADR 0010 — операція накопичення належить місяцю свого створення; накопичення, створене під час первинного налаштування, отримує статус «Активне»; початковий баланс не є фінансовим записом. **Уточнено:** A-27, ADR 0011 — поповнення поточного місяця можна редагувати й видаляти, минулого — лише перегляд; витрата з накопичення — звичайна витрата; будь-яке нове накопичення отримує статус «Активне». **Уточнено:** A-28, ADR 0012 — архівування є окремим виміром і не змінює ні залишку, ні статусу; архівоване накопичення можна розархівувати; назва обов'язкова, не унікальна. **Уточнено:** A-29, ADR 0013 — архівувати можна лише «Закрите»; після розархівування воно лишається «Закритим»; залишок архівованого накопичення входить до загальної доступної суми. |
| A-24 | **O-12:** валюта в першому релізі | Усі грошові величини першого релізу — у гривнях (UAH), без винятків: доходи та їхні залишки, витрати, загальний нерозподілений залишок, накопичення (баланс, поповнення, початковий залишок, цільова сума), базовий мінімум, борги та погашення, підсумки періодів, загальна доступна сума. Вибору валюти, поля валюти, валютних налаштувань, мультивалютності, курсів, обміну валют і будь-якої конвертації немає. Код валюти не зберігається; `currency_code`, сутність, таблиця чи перелік валют, репозиторій валют і сервіс обміну не вводяться. Гроші — цілі числа в мінімальних одиницях (копійках), без `float`. Валюта витрати збігається з валютою джерела. Позначку валюти при відображенні сум постійно показувати не потрібно. ADR 0002, 0003, 0007 не змінюються. Деталі — ADR 0008. |
| A-25 | **O-11:** життєвий цикл доходу та модель календарного місяця | Бюджетний період — календарний місяць (часова зона `Europe/Kyiv`); окремої сутності бюджетного періоду й окремого запису в базі для місяця немає. Дохід має суму, належність до календарного місяця й назву / опис; точний день не зберігається. Дохід автоматично належить поточному місяцю; створити його в майбутньому чи минулому місяці не можна. Після створення дохід не змінюється; помилка виправляється новим доходом. Фізичного видалення, скасування, відміни дії й відновлення немає. Статус визначає система: залишок > 0 — «Активний», 0 — «Завершений»; при нульовому залишку дохід автоматично архівується. Архівований дохід не може бути джерелом нових операцій. Під час першого запуску в новому місяці попередній місяць обробляється автоматично: позитивні залишки доходів консолідуються в загальний нерозподілений залишок, доходи архівуються. Після тривалої перерви порожні місяці пропускаються, а для минулих місяців із позитивними залишками доходів показується один загальний діалог «Перенести / Вилучити» без автоматичного вибору; накопичення й базовий мінімум у ньому не беруть участі. Наслідки для вже проведених витрат і поповнень не визначаються. Деталі — ADR 0009. |
| A-26 | **Q151–Q167:** календарна належність фінансових операцій і стартові залишки | Фінансові записи — дохід, звичайна витрата (зокрема з накопичення) й поповнення накопичення (уточнено A-27); запис залишається фінансовим записом незалежно від залишку. Кожен запис належить календарному місяцю свого створення (`Europe/Kyiv`); місяць визначає система, заднім числом запис не створюється; поповнення з кількох джерел — одна операція одного місяця. Звичайну витрату можна редагувати й видаляти лише в поточному місяці; після переходу місяця вона доступна лише для перегляду. Правила редагування поповнень — A-27. Місяць без фінансових записів, що залишилися, вважається порожнім; окрема ознака активності місяця не зберігається. Під час первинного налаштування: один початковий баланс доходу одразу зараховується до загального нерозподіленого залишку без створення доходу й без відстеження походження; для кожного накопичення можна ввести початковий баланс (зокрема створити накопичення з балансом, також 0) — це не поповнення; таке накопичення отримує статус «Активне». Початкові баланси не є фінансовими записами й не мають календарного місяця. Деталі й питання, що потребують рішення, — ADR 0010. |
| A-27 | **Q168–Q173:** редагування операцій, межі первинного налаштування, закриття O-10 | Зміна чи видалення звичайної витрати, яка довела залишок доходу до 0 і спричинила його архівування, заблокована: архівований дохід не відновлюється, новий дохід, переказ чи компенсуюча операція не створюються. У поточному місяці звичайну витрату можна редагувати за сумою, назвою / описом і джерелом; недопустима нова конфігурація не зберігається (без від'ємного залишку, автоматичної зміни джерела, поділу чи добору). Витрата з накопичення — звичайна витрата, не окремий тип. Поповнення накопичення можна редагувати й видаляти в поточному місяці атомарно для всіх джерел і накопичення; недостатність коштів блокує зміну; поповнення минулого місяця — лише перегляд. Первинне налаштування завершується першим успішним завершенням майстра; після цього стартові баланси не змінюються, майстер повторно не відкривається, зміни — лише звичайними операціями. Будь-яке нове накопичення отримує статус «Активне». O-10 закрито як неактуальне після O-11. Деталі й питання, що потребують рішення, — ADR 0011. |
| A-28 | **Q174–Q185:** редагування поповнень, незавершене первинне налаштування, архівування накопичень | Зміна чи видалення поповнення, що відновила б залишок уже архівованого доходу, заборонена (як для звичайної витрати). У поточному місяці поповнення можна повністю редагувати (джерела, суми частин, накопичення-отримувач, назва, опис); нова конфігурація перевіряється атомарно, недопустима не зберігається; зміна лише назви чи опису не змінює залишків; минулий місяць — лише перегляд. Незавершений майстер первинного налаштування зберігається без строку дії, його можна продовжити або повністю скинути; до завершення фінансові записи не створюються, правила переходу між місяцями не застосовуються. Накопичення має три незалежні виміри: залишок, статус життєвого циклу («Активне», «Досягнуте», «Закрите») і архівність. Архівування не змінює залишку й статусу, приховує накопичення зі звичайного переліку й забороняє нові витрати з нього та нові поповнення в нього; розархівування не є фінансовою операцією й не змінює статусу (уточнено A-29: архівованим може бути лише «Закрите»). Назва обов'язкова, не унікальна; назву й опис можна редагувати, зокрема в архіві. Фізичного видалення накопичення немає. Деталі й питання, що потребують рішення, — ADR 0012. |
| A-29 | **Q186–Q190:** межі архівування накопичень і межа первинного налаштування | Архівувати можна лише накопичення зі статусом «Закрите»; допустимі комбінації — «Активне», «Досягнуте» чи «Закрите» без архівування та «Закрите + архівоване». Розархівування повертає «Закрите + неархівоване» без зміни статусу й залишку. Залишок архівованого накопичення входить до загальної доступної суми, але воно не є джерелом нових операцій. Поки накопичення архівоване, його статус не змінюється, а пов'язані з ним витрати й поповнення поточного місяця не редагуються й не видаляються; для змін його спершу розархівовують (уточнено A-30: назву й опис таких операцій змінювати можна). До першого успішного завершення майстра первинного налаштування нормальна фінансова робота недоступна: доходи, витрати й поповнення не створюються. Деталі — ADR 0013. |
| A-30 | **Q191:** метадані операцій архівованого накопичення | Заборона редагувати операції поточного місяця, пов'язані з архівованим накопиченням (A-29), стосується лише змін, що впливають на фінансовий стан: суми, джерел, розподілу сум, накопичення-отримувача, видалення. Назву й опис таких операцій змінювати можна: це не змінює залишків, статусу й архівності накопичення та не відновлює архівований дохід. Архівування блокує фінансові зміни, але не обов'язково нефінансові метадані. Операції минулих календарних місяців повністю доступні лише для перегляду. Деталі — ADR 0014. |
| A-31 | **O-1:** ідентичність продукту | Остаточні значення для `product.toml`: `<ProductName>` = `Budget`, `<Publisher>` = `Budget`, `AppId` = `5534B0BB-9852-4C19-8043-7486FC92928A`, `<AppUserModelID>` = `Budget.Budget`, `<ExecutableName>` = `Budget`, `<InstallerBaseName>` = `Budget-Setup`, `<DataDirectoryName>` = `Budget`. `AppId` після першого публічного релізу не змінюється. Деталі — ADR 0015. |
| A-32 | **O-7:** екрани першого релізу | Шість екранів: майстер первинного налаштування (обов'язковий до завершення), огляд, місяць (поточний і минулі, минулі — лише перегляд), накопичення (з розділом архіву), борги, сервіс (резервні копії й відновлення). Форми операцій і системні діалоги (спеціальний діалог після тривалої перерви, відновлення після пошкодження, підтвердження, повідомлення про заблоковані зміни) — не окремі екрани. Рахунків, валют, поділу «базові / бажані», окремих цілей, планів і графіків немає. Деталі — ADR 0016. |
| A-33 | **O-8:** хвилини GitHub Actions | Схема розділу 5.6 — остаточна політика, розрахована на приватний репозиторій. Без cron, нічних збірок і матриць; `concurrency` зі скасуванням застарілих запусків; зміни лише документації не запускають `ci.yml`; ручний запуск для `build-check` і `release.yml`. Windows-перевірки не прибираються. Деталі — ADR 0017. |
| A-34 | **O-9:** модель боргу | Борг — окремий запис зобов'язання (назва, опис, сума, залишок); не дохід, не джерело витрати, не рахунок. Отримання позикових коштів — фінансова операція: створює новий борг і зараховує суму до загального нерозподіленого залишку; витрата за рахунок позикових коштів — звичайна витрата з цього залишку, без прив'язки до боргу. Погашення — окрема фінансова операція з одного вручну обраного джерела (активний дохід, нерозподілений залишок, неархівоване накопичення); не є звичайною витратою; не перевищує ні залишку джерела, ні залишку боргу. Статус «Активний» / «Погашений» визначає система за залишком. Операції боргу належать місяцю створення; редагування й видалення — лише в поточному місяці за загальними правилами; минулі — лише перегляд. Під час переходу місяця борг не змінюється. Початкові борги вводяться в майстрі первинного налаштування й не зараховуються до нерозподіленого залишку. Борг не зменшує загальної доступної суми й показується окремо. Відсотків, лімітів, графіків, кредиторів як сутностей і дебіторської заборгованості немає. Деталі — ADR 0018. |
| A-35 | **O-14:** поняття «планування» | Окремої функції планування в першому релізі немає: немає планів, лімітів, «план — факт», попереднього розподілу доходу. «Планування» означає наявні механізми: базовий мінімум місяця, накопичення з необов'язковою цільовою сумою, загальну доступну суму й залишки джерел. | A-36 | **O-13:** накопичення в аналізі періоду | Аналіз календарного місяця: доходи місяця; фактичні витрати — усі звичайні витрати незалежно від джерела, зокрема з накопичень (з можливою розбивкою за типом джерела); порівняння з базовим мінімумом (інформаційне); окремо — поповнення накопичень, погашення боргів, отримані позикові кошти. Поповнення не входить до фактичних витрат: це переміщення коштів, а не споживання. Окремий блок руху накопичень за місяць. Початковий баланс не має місяця й у русі місяця не показується. Поточні залишки накопичень (зокрема архівованих) — у загальному огляді, без знімків на кінець місяців. Графіків і багатомісячних звітів немає. Деталі — ADR 0020. |

| A-38 | Рішення за підсумками дизайн-рев'ю | Назва обов'язкова для доходу, звичайної витрати й поповнення; опис необов'язковий. ### Терміни (A-18)

Поняття **базовий мінімум**, **фактичні витрати**, **перевищення базового мінімуму**, **залишок** і **борг** — різні й не ототожнюються. Визначення — в ADR 0002. Термін «перевитрата» не використовується як синонім перевищення базового мінімуму.

### Терміни (A-19)

**Конкретний дохід** — окреме джерело фактично отриманих коштів із власним залишком (не категорія, не резерв, не рахунок). **Джерело витрати** — активний дохід, «Загальний нерозподілений залишок» або накопичення; одна витрата має рівно одне джерело, яке обирає користувач. **Завершений дохід** — дохід із нульовим залишком; прибирається з активних джерел, але зберігається в історії. **Загальний нерозподілений залишок** — окреме джерело, до якого наприкінці бюджетного періоду консолідуються невикористані залишки доходів. **Розподіл** — фактична витрата, а не план. **Накопичення («банка»)** — накопичувальна категорія й допустиме джерело витрати; не рахунок і не заблоковані кошти. **Загальний доступний залишок** — загальний нерозподілений залишок разом із залишками накопичень і активних доходів. Визначення — в ADR 0003.

### Дизайн-рев'ю

**Візуальний напрям зафіксовано:**
- premium;
- беж і приглушений зелений (beige + muted green);
- редакційний характер (editorial);
- стриманість (restrained);
- багато вільного простору (whitespace).

**Заборонено:**
- «фінтех»-синій;
- кислотний зелений;
- glassmorphism;
- надмірні тіні;
- візуальний шум.

Hex-коди з Додатка C — **попередні дизайн-токени, а не фінальний дизайн**. Від них не переходимо безпосередньо до масової реалізації інтерфейсу. Окремий design review обов'язковий після визначення основних екранів (R-6). **Завершено:** A-37, ADR 0021 — затверджені значення в `docs/design/design-system.md`.

### 5.2. Шари та напрям залежностей

```
ui ──▶ services ──▶ domain
          │            ▲
          └──▶ storage ┘
platform ◀── app (складає все разом)
```

| Шар | Що містить | Що йому заборонено |
|---|---|---|
| `domain` | Сутності, `Money`, правила розрахунку (наприклад, залишок, перевищення базового мінімуму), перевірки | Імпортувати Qt, `sqlite3`, файлову систему; використовувати `float` |
| `storage` | З'єднання з базою, репозиторії, міграції, резервні копії, перевірка цілісності | Містити бізнес-правила; імпортувати Qt |
| `services` | Сценарії (один сценарій — одна транзакція), координація domain і storage | Імпортувати Qt; писати SQL напряму |
| `ui` | Віджети, екрани, тема, форматування для показу | Писати SQL; містити бізнес-правила; задавати кольори поза `theme/` |
| `platform` | Шляхи Windows, блокування від запуску другої копії, AppUserModelID | Містити бізнес-логіку |

- Межі між шарами перевіряє тест на імпорти в CI. Інструмент на зразок import-linter можна додати лише за окремим рішенням, бо це нова залежність.
- Логіка не залежить від Qt. Тому `domain`, `storage` і `services` тестуються без інтерфейсу, зокрема на Linux.

### 5.3. Межі даних і сховища

- **Розташування.** Користувацькі дані зберігаються в `%LOCALAPPDATA%\<DataDirectoryName>\` (значення з `product.toml`):
  - `budget.db` (+ `-wal`, `-shm`);
  - `backups/`;
  - `settings.json`;
  - `logs/`.

  Шлях один і той самий для встановленої та portable-версії. Тека програми й «Документи» для даних не використовуються: «Документи» часто синхронізує OneDrive, а це конфліктує з файлами WAL.
- **Підключення.** При кожному підключенні виставляються `journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON`, і всі таблиці мають тип `STRICT`.
- **Транзакції.** Відкриває їх лише шар `services` (`BEGIN IMMEDIATE`): одна дія користувача — одна транзакція. `storage` не робить commit самостійно.
- **Часова зона.** Фінансова часова зона — `Europe/Kyiv` (ADR 0009), визначена лише в `domain/calendar.py`. На Windows системна база часових поясів IANA не гарантована, тому залежність `tzdata` обов'язкова для Windows: вона забезпечує однакову поведінку `ZoneInfo`. Альтернативного механізму часових зон немає.
- **Гроші.** У домені грошове значення представлене типом `Money`. У першому релізі всі грошові величини — у гривнях (UAH); код валюти не зберігається ні в доменній моделі, ні в базі (A-24, ADR 0008). Для зберігання суми використовується `INTEGER` у мінімальних одиницях (копійках); схема бази цим пунктом не проєктується. Користувацьке введення розбирається з рядка в `Decimal`, правило округлення задається явно. `float` для грошей не використовується; це перевіряється в CI.
- **Запуск:**
  1. блокування від запуску другої копії;
  2. `quick_check`;
  3. щоденна резервна копія;
  4. міграції — лише після обов'язкової резервної копії, кожна в окремій транзакції;
  5. нумерація міграцій лише вперед, номер схеми в `user_version`.
- **Пошкодження бази.** Застосунок нічого не записує, перейменовує пошкоджений файл і пропонує відновитися з останньої справної копії.
- **Налаштування.** Записуються атомарно: тимчасовий файл, потім `os.replace`. **У базі даних налаштування інтерфейсу не зберігаються.**
- **Видалення.** Деінсталятор видаляє цю теку **лише** тоді, коли користувач явно поставив галочку (A-5). Тихе видалення (`/SILENT`) її не видаляє ніколи (AC-1).

Детальні вимоги — Додаток B.

### 5.4. Межі дизайн-системи

- **`ui/theme/tokens.py`** — єдине місце зі значеннями. Значення мають два рівні:
  - **базова палітра**, наприклад `sage-300`;
  - **семантичні ролі**: `bg`, `surface`, `text`, `text-muted`, `primary`, `danger`…

  Компоненти звертаються **лише до семантичних ролей**. Тому палітру можна змінити, а пізніше й додати темну тему, не чіпаючи компоненти.
- **Категорії токенів:** кольори, типографіка (гарнітури, розміри, товщини, цифри однакової ширини для сум), відступи, радіуси, тіні (не більше одного стриманого рівня), розміри елементів, стани (hover / pressed / focus / disabled / error), іконки.
- **Як токени потрапляють у віджети.** Шаблон QSS отримує значення з токенів, плюс налаштовується `QPalette`. Іконки інтерфейсу — монохромні SVG, які перефарбовуються кольором з токенів. Кандидат — набір Lucide (ліцензія ISC).
- **Контроль у CI:**
  - тест шукає hex-кольори поза `ui/theme/`;
  - тест перевіряє контраст пар «текст/фон» за WCAG AA.
- **Статус значень.** Остаточні значення затверджено дизайн-рев'ю R-7 і наведено в `docs/design/design-system.md` (A-37, ADR 0021); значення Додатка C — історичні попередні.
- **Тексти інтерфейсу.** Перекладні рядки — лише через механізм Qt (`tr`). Форматування сум і дат — лише через `QLocale` (українська мова: кома як десятковий роздільник, три форми множини).
- **Іконка застосунку.** Потрібні такі файли:
  - `assets/icon/budget.svg` — векторний оригінал, єдине джерело;
  - `assets/icon/budget.ico` з розмірами 16, 20, 24, 32, 40, 48, 64, 256 (256 у стисненні PNG);
  - `assets/icon/png/` — PNG тих самих розмірів для вікна (`QIcon`);
  - `assets/installer/` — графіка майстра встановлення: велика бічна (164×314 та масштаби 125–250 %) і мала (55×55 та масштаби).

  Один і той самий набір використовують `.exe`, інсталятор, ярлики, запис видалення й вікно. Рекомендація для design review: окремо перевірити читабельність іконки на малих розмірах 16–24 px; за потреби може бути створено спрощений варіант малюнка.
- **Обмеження Qt, які треба врахувати в дизайні:**
  - QSS не підтримує `box-shadow` і анімацію переходів. Тіні — через `QGraphicsDropShadowEffect` (точково, бо дорогий у відмальовуванні) або відтінками й тонкими рамками.
  - Рекомендація: за замовчуванням зберігати системну рамку вікна, бо власна безрамкова шапка може порушити прилипання вікон, масштабування та доступність. На Windows 11 колір заголовка можна підлаштувати під палітру через системний API. Остаточне рішення щодо рамки вікна та оформлення вікна (chrome) приймається під час design review. **Вирішено:** системна рамка зберігається, колір заголовка на Windows 11 — `bg` (`docs/design/design-system.md`, розділ 4).

### 5.5. Структура пакування та релізу

```
pyproject.toml (версія) ─┐
product.toml (назва…) ───┼─▶ PyInstaller (onedir, іконка, ресурс версії)
                         │        └─▶ dist/<ExecutableName>/<ExecutableName>.exe
                         │              ├─▶ [крок «підпис»: .exe]   ← вимкнено (Q3)
                         │              ├─▶ ISCC /DAppVersion /DAppId /DAppName …
                         │              │     └─▶ <InstallerBaseName>-x.y.z.exe
                         │              │           └─▶ [крок «підпис»: інсталятор] ← вимкнено
                         │              └─▶ (необов'язково) <ExecutableName>-x.y.z-portable.zip
                         └─▶ SHA256SUMS.txt → GitHub Release
```

- **Inno Setup** отримує всі ідентифікатори як параметри компіляції. У `.iss` вони не прописані.
- **Як потім увімкнути підпис (Q3):**
  - у самому конвеєрі вже є окремі кроки підпису, які вмикаються за наявності секрету сертифіката;
  - у Inno Setup для цього є директиви `SignTool` і `SignedUninstaller`.

  Підпис додається без перебудови пакування.
- **Перевірки після збірки:**
  - `<ExecutableName>.exe --self-check` запускається без екрана й завершується з кодом 0;
  - тихе встановлення;
  - перевірка, що є файли, обидва ярлики й запис у HKCU;
  - тихе видалення;
  - перевірка, що **дані залишилися** (AC-1).

Деталі налаштувань Inno Setup і механізм ярликів — Додаток A.

### 5.6. Структура CI

| Workflow | Коли запускається | Runner | Що робить |
|---|---|---|---|
| `ci.yml` / `lint` | кожен push і PR | `ubuntu-latest` | `ruff check`, `ruff format --check` |
| `ci.yml` / `core-tests` | кожен push і PR | `ubuntu-latest` | pytest для `domain`, `storage`, `services`; тести меж шарів і заборони `float` |
| `ci.yml` / `windows-tests` | PR у `main` і push у `main` | `windows-latest` | Повний pytest, включно з тестами інтерфейсу (pytest-qt, `QT_QPA_PLATFORM=offscreen`) і тестами токенів |
| `ci.yml` / `build-check` | push у `main` (або вручну) | `windows-latest` | PyInstaller і `--self-check`, без інсталятора |
| `release.yml` | тег `v*` або ручний запуск | `windows-latest` | Тести, PyInstaller, (підпис), Inno Setup, перевірка встановлення й видалення, (ZIP), SHA256, GitHub Release |

- Inno Setup встановлюється в робочому процесі явно (наприклад `choco install innosetup`), без розрахунку на образ runner'а.
- Python і uv фіксуються однаковими версіями в усіх завданнях.
- Політика використання хвилин (O-8): без cron, нічних збірок і матриць; `concurrency` зі скасуванням застарілих запусків; зміни лише документації не запускають `ci.yml` (A-33, ADR 0017).
- Windows 10 у GitHub Actions недоступна (runner'и — Windows Server). Тому **ручна перевірка першого інсталятора на Windows 10 і 11** входить до списку перевірок перед релізом.
- Тимчасовий `AppId` дозволений для внутрішніх тестових збірок і заборонений для першого та будь-якого публічного релізу. `release.yml` має блокувати саме **публічний** реліз із тимчасовим `AppId` (див. O-1). Це не означає, що конвеєр для внутрішніх тестових збірок потрібно реалізовувати вже зараз. **Уточнено:** A-31, ADR 0015 — остаточний `AppId` уже визначено; перевірка залишається запобіжником.

| Ризик | Рівень | Що робимо |

| Інструменти перекладу Qt (`pyside6-lupdate`, `pyside6-lrelease`) у пакеті Essentials | Низький | Перевірити наявність під час підготовки середовища; запасний варіант — стандартний модуль `gettext`. |

### A.1. Конвеєр збірки

```
джерельний код → PyInstaller (onedir) → dist\<ExecutableName>\<ExecutableName>.exe + бібліотеки
                                          ├─→ Inno Setup (ISCC) → <InstallerBaseName>-x.y.z.exe
                                          └─→ ZIP (необов'язково) → <ExecutableName>-x.y.z-portable.zip
```

### A.2. Ключові налаштування Inno Setup (`packaging/inno/budget.iss`)

| Параметр | Значення | Навіщо |
|---|---|---|
| `AppId` | GUID із `product.toml`. Остаточне значення — `5534B0BB-9852-4C19-8043-7486FC92928A` (A-31, ADR 0015); після першого публічного релізу **ніколи не змінюється** | Інсталятор розпізнає попередню версію й оновлює її, а не ставить другу копію. |
| `AppName` / `AppVersion` / `AppPublisher` | з `product.toml` і `pyproject.toml`, передаються через `ISCC /D…`; так само передаються `<ExecutableName>` і `<InstallerBaseName>` | Одне джерело для всього. |
| `PrivilegesRequired` | `lowest`, без вибору режиму (A-2) | Встановлення лише для поточного користувача, без прав адміністратора. |
| `DefaultDirName` | `{autopf}\<ProductName>` | За режиму `lowest` це `%LOCALAPPDATA%\Programs\<ProductName>`. |
| `SetupIconFile` | `assets\icon\budget.ico` | Іконка самого інсталятора. |
| `UninstallDisplayIcon` | `{app}\<ExecutableName>.exe` | Іконка в списку встановлених програм. |
| `WizardImageFile` / `WizardSmallImageFile` | власна графіка з `assets/installer/` | Прибирає стандартне оформлення Inno. |
| `CloseApplications=yes` + `AppMutex` | — | Перед оновленням інсталятор просить закрити запущений застосунок. |

### A.3. Як саме з'явиться ярлик на Desktop

У секції `[Icons]` будуть два записи:

```
Name: "{autoprograms}\<ProductName>"; Filename: "{app}\<ExecutableName>.exe"; AppUserModelID: "<AppUserModelID>"
Name: "{autodesktop}\<ProductName>";  Filename: "{app}\<ExecutableName>.exe"; AppUserModelID: "<AppUserModelID>"
```

- **Ярлик обов'язковий.** Стандартний шаблон Inno робить ярлик на робочому столі необов'язковою галочкою, вимкненою за замовчуванням. Тут ярлик навмисно **не прив'язаний** до параметра `Tasks`, тому створюється завжди.
- За встановлення для поточного користувача `{autodesktop}` — це робочий стіл поточного користувача.
- Іконку ярлик бере з ресурсу `<ExecutableName>.exe`, куди її вбудовує PyInstaller.
- Однаковий `AppUserModelID` у ярлику та в застосунку потрібен, щоб на панелі завдань показувалася іконка застосунку, а не іконка Python. Значення береться з `product.toml`.
- Під час видалення обидва ярлики прибираються автоматично.
- Назва ярлика — `<ProductName>`, тобто `Budget` (A-31, ADR 0015).

### A.4. Видалення і дані користувача

- Inno автоматично реєструє запис для штатного видалення Windows у HKCU.
- Видаляються файли застосунку, ярлики й запис у реєстрі.
- Тека даних `%LOCALAPPDATA%\<DataDirectoryName>\` за замовчуванням **залишається**.
- Інтерактивне видалення показує власне вікно з галочкою «Видалити також мої дані», **вимкненою за замовчуванням**.
- **`/SILENT` ніколи не видаляє дані користувача, незалежно від стану інтерактивної опції** (AC-1).

## Додаток B. Вимоги до безпеки даних (DS-1…DS-10)

> Цей додаток є технічною деталізацією вже затверджених рішень розділів 1–5. Він не вводить нових продуктових або архітектурних рішень. Якщо положення цього додатка суперечить затвердженому рішенню або відкритому питанню, пріоритет має затверджене рішення та/або відкрите питання.

| № | Вимога | Як реалізується |
|---|---|---|
| DS-1 | Гроші | У першому релізі кожне грошове значення — у гривнях (UAH); код валюти не зберігається (A-24, ADR 0008). Сума зберігається як `INTEGER` у мінімальних одиницях (копійках). У логіці — тип `Money`, усередині якого `int` або `Decimal`. Введення користувача розбирається з рядка в `Decimal`; правило округлення фіксується явно. **`float` заборонений** — це перевіряють тест і пошук у CI. |
| DS-2 | Атомарність | Одна дія користувача — одна транзакція (`BEGIN IMMEDIATE … COMMIT`, відкат при помилці). Транзакції керуються явно, без неявної поведінки модуля `sqlite3`. |
| DS-3 | Стійкість до переривань | `journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON`. Незавершена транзакція (збій живлення, примусове закриття) автоматично відкочується. |
| DS-4 | Цілісність | Таблиці `STRICT`, обмеження `CHECK`, зовнішні ключі. `PRAGMA quick_check` при запуску, повний `integrity_check` перед резервною копією. |
| DS-5 | Резервні копії | Через вбудоване API `Connection.backup()` (узгоджена копія під час роботи). Коли: щодня при першому запуску, **обов'язково перед кожною міграцією**, перед відновленням, на вимогу. Ротація за замовчуванням: 7 щоденних + 4 щотижневі + 12 щомісячних. Кожна копія після запису перевіряється на цілісність. |
| DS-6 | Відновлення | Якщо перевірка виявила пошкодження: застосунок **нічого не записує**, пошкоджений файл перейменовує й зберігає, пропонує відновлення з останньої справної копії. |
| DS-7 | Міграції | Нумеровані, лише вперед. Версія схеми — у `PRAGMA user_version`. Кожна міграція — одна транзакція після резервної копії. Тести проганяють увесь ланцюжок міграцій від порожньої бази. |
| DS-8 | Один процес | Блокування через `QLockFile`: друга копія застосунку не відкриє ту саму базу на запис. |
| DS-9 | Розташування даних | База — у `%LOCALAPPDATA%\<DataDirectoryName>\`, а не в теці програми й не в «Документах». Налаштування — JSON з атомарним записом (тимчасовий файл + `os.replace`). |
| DS-10 | Експорт | Пізніше (D-6) — експорт у відкритий формат (CSV/JSON) як незалежний від бази шлях порятунку даних. |

Схема бази, перелік таблиць і доменні сутності **тут не визначаються** — визначаються на етапі проєктування за затвердженими рішеннями.
