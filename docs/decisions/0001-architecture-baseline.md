# ADR 0001. Архітектурна основа

- **Статус:** прийнято
- **Дата:** 2026-10-05
- **Джерело:** [`docs/architecture.md`](../architecture.md), розділ 1 (A-1…A-17)

## Контекст

`Budget` (робоча назва) — desktop-застосунок для Windows для керування персональним бюджетом. До початку реалізації потрібно зафіксувати технологічну основу та обов'язкові архітектурні принципи, щоб подальші рішення спиралися на погоджену базу.

Бізнес-модель і схема бази даних цим ADR **не визначаються**. Вони залежать від відкритих питань O-2…O-6 (див. `architecture.md`, розділ 4) і будуть зафіксовані окремими ADR після відповідей.

## Рішення

### Технологічний стек

| Призначення | Рішення |
|---|---|
| Мова | Python 3.12 |
| Інтерфейс | PySide6-Essentials (Qt 6) |
| Сховище | SQLite (модуль `sqlite3` стандартної бібліотеки) |
| Керування залежностями | uv |
| Тести | pytest, pytest-qt |
| Перевірка й форматування коду | ruff |
| Збірка `.exe` | PyInstaller у режимі onedir |
| Інсталятор | Inno Setup 6 |
| CI та випуски | GitHub Actions; Windows-збірки на `windows-latest` |

### Шари

Код розділяється на шари `domain`, `storage`, `services`, `ui`, `platform` з однобічними залежностями:

```
ui ──▶ services ──▶ domain
          │            ▲
          └──▶ storage ┘
platform ◀── app (складає все разом)
```

- `domain` не залежить від Qt, SQLite і файлової системи.
- Транзакціями керує лише `services`.
- `ui` не містить SQL і бізнес-правил.

### Сховище і гроші

- SQLite у режимі WAL, таблиці `STRICT`, `foreign_keys=ON`, `synchronous=FULL`.
- Атомарні транзакції: одна дія користувача — одна транзакція.
- Резервні копії, перевірка цілісності, відновлення після пошкодження, міграції лише вперед — частина архітектури з першого дня.
- Гроші представлені без втрати точності разом із валютою на рівні доменної моделі (`Decimal`/`int`). **`float` для грошей заборонений.** Фізичне розташування коду валюти в схемі бази цим ADR не визначається (залежить від O-3).
- Дані користувача зберігаються в `%LOCALAPPDATA%\<DataDirectoryName>\`.

### Інсталятор

- Основний спосіб розповсюдження — інсталятор `.exe` (Inno Setup).
- Встановлення лише для поточного користувача, без прав адміністратора.
- Ярлики на Desktop і в Start Menu створюються автоматично.
- Штатне видалення через Windows.
- Дані користувача під час видалення **не видаляються**; видалення даних — лише окремою явною опцією, вимкненою за замовчуванням. `/SILENT` ніколи не видаляє дані.
- Ідентифікатори продукту (назва, видавець, `AppId`, AppUserModelID, назва теки даних, ім'я виконуваного файлу, базова назва інсталятора) беруться з одного конфігураційного файлу (`product.toml`) й не прописуються в коді чи скриптах вручну.
- Цифровий підпис у першому релізі відсутній; конвеєр передбачає можливість додати його пізніше без перебудови пакування.

### Дизайн-система

- Усі візуальні значення (кольори, типографіка, відступи, радіуси, тіні, розміри елементів, стани, іконки) централізовані в `ui/theme/`.
- Компоненти використовують лише семантичні токени; кольори в окремих компонентах не прописуються.
- Конкретні значення токенів — попередні до окремого design review.

## Що цей ADR НЕ вирішує

- Фінальну назву продукту, видавця та фінальний `AppId` (O-1).
- Модель нерозподіленого доходу (O-2).
- Рахунки (O-3).
- Правила бюджетних періодів і перенесення залишків/перевитрат (O-4).
- Семантику «базова / бажана» витрата (O-5).
- Фінансові цілі (O-6).
- Екрани першого релізу (O-7).
- Обмеження щодо хвилин GitHub Actions (O-8).
- Фінальні значення дизайн-токенів і шрифти (design review).
- Схему бази даних і доменні сутності.

## Наслідки

- Доменну логіку та сховище можна тестувати без Windows і без Qt.
- Windows-специфічні перевірки (інтерфейс, збірка, встановлення) виконуються в Windows CI та вручну перед релізом.
- Зміна будь-якого пункту цього ADR оформлюється новим ADR, що його замінює.
